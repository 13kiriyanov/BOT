# Polymarket Short-Term Crypto Market Maker

Бот для маркет-мейкинга на краткосрочных (5–15 мин) рынках BTC/ETH Up-or-Down
на Polymarket CLOB. Стратегия: двустороннее котирование с накоплением полных
пар, мгновенный merge пар в USDC, управление инвентарём и слабый directional
наклон от модели fair value по споту.

- **Adverse selection.** Маркет-мейкинг на 5-минутных крипторынках — среда, где
  против вас торгуют участники с колокацией и прямыми фидами бирж. Ваш ордер
  исполняется чаще всего именно тогда, когда цена собирается пойти против вас.
  Симулятор в этом репозитории показывает: при доле информированного потока
  выше ~0.6 стратегия становится убыточной. Оценить эту долю заранее нельзя.
- **Нет тестнета.** Polymarket не предоставляет sandbox или paper-trading.
  Любая проверка на живом рынке — это реальные деньги.
- **Технический риск.** Разрыв WebSocket, зависший цикл, изменение API,
  расхождение локального учёта позиций с реальностью — каждое из этого может
  привести к неконтролируемой позиции. Риск-модули здесь снижают вероятность,
  но не устраняют её.
- **Модельный риск.** Страйк рынка часто приходится калибровать косвенно
  (см. раздел «Проблема страйка»). Неверный страйк = систематически смещённая
  оценка = систематические убытки.
- **Юридический риск.** Вы обязаны самостоятельно проверить geo-restrictions
  Polymarket, их Terms of Service и законодательство своей юрисдикции
  **до** запуска. В ряде стран доступ к платформе ограничен, а
  автоматизированная торговля событийными контрактами может подпадать под
  регулирование.

**Это не финансовая рекомендация.** Автор кода не несёт ответственности за
ваши убытки. Используйте отдельный кошелёк с суммой, потеря которой не

## Как это на самом деле работает

### Поправка, которую важно понять до запуска

Распространённое заблуждение: «ищем рынки, где `yes_ask + no_ask < 0.99`, и
покупаем обе стороны». **Такой возможности не существует.** Матчинг-движок
Polymarket трактует YES и NO как дополняющие друг друга: покупка NO по цене
`p` тождественна продаже YES по `1 − p`. Стаканы зеркальны:

```
ask_NO ≡ 1 − bid_YES
bid_NO ≡ 1 − ask_YES
```

Тейкерский арбитраж внутри одного рынка арбитражируется самим движком.

Реальная стратегия — **мейкерская**. Мы ставим `BUY YES @ a` и `BUY NO @ b`
так, что `a + b < 1`, и ждём пассивного исполнения обеих ног. Получив пару,
имеем актив, стоящий ровно $1 при любом исходе, купленный за `a + b`.

При этом заметьте:

```
bid_YES = a
ask_YES = 1 − b          (покупка NO по b == продажа YES по 1−b)
spread  = 1 − (a + b)
```

**«Накопление пар с суммой 0.985» и «котирование с полуспредом 0.75 цента
вокруг fair value» — это буквально одно и то же действие.** Поэтому в боте
один модуль (`quoting.py`) делает и то, и другое: вы задаёте целевую
стоимость пары, из неё выводится спред.

### Откуда берётся прибыль (по убыванию значимости)

1. **Захват спреда на обеих ногах.** Основа. `1 − target_pair_cost` за пару.
2. **Мгновенный merge.** `merge_positions()` превращает пару YES+NO обратно в
   $1 USDC, не дожидаясь резолюции. Без этого капитал заморожен до конца
   окна, и бот делает 1–2 круга вместо десятков. **Это то, что делает
   стратегию высокочастотной.**
3. **Liquidity rewards.** У многих рынков есть `rewards_max_spread` и
   `rewards_min_size`. Котирование внутри этой полосы приносит выплаты,
   часто сопоставимые с торговым PnL. Бот автоматически ужимает спред внутрь
   reward-полосы.
4. **Directional edge.** Самый маленький и самый рискованный компонент.
   Его роль — не «заработать на направлении», а **не оказаться на
   неправильной стороне**, когда BTC двинулся, а рынок ещё не переставился.

### Модель fair value: среднее по окну, а не конечная точка

Правила живых updown-рынков (подтверждены по описанию): исход считается по
**TWAP Chainlink за окно** — Up, если среднее за окно ≥ значения того же
ряда в начале окна («not according to any other sources or spot markets»).
Поэтому модель спрашивает не «где цена закончит», а «каким будет среднее»:

```
TWAP = α·A_реал + β·A_ост,   α — доля окна позади, β = 1 − α
P(TWAP ≥ K) = P(A_ост ≥ K_eff),   K_eff = (K − α·A_реал) / β
d = ( ln(S/K_eff) + (μ − σ²/2)·τ/2 ) / ( σ·√(τ/3) )
```

`A_реал` — уже реализованное среднее, бот накапливает его сам по фиду
резолюции (`RealizedTwap`). Дисперсия среднего остатка — `σ²τ/3` (втрое
меньше дисперсии конца), дрейф входит половиной. Следствия: модель
увереннее точечной при том же отклонении; к концу окна реализованная часть
«запирает» исход (при `α·A_реал > K` вероятность равна 1 при любом споте);
одиночный шип цены почти не двигает среднее.

Практические поправки, без которых модель бесполезна на минутных горизонтах:

- `σ` — EWMA реализованной волатильности по тикам **фида резолюции**
  (полупериод 45 с). Статичная волатильность на таком горизонте не работает.
- `μ` — momentum из EWMA доходностей, **зажатый в одно стандартное
  отклонение остатка**. Momentum крипты на минутах шумный.
- При `τ → 0` модель сингулярна. Доверие к ней (`confidence`) падает до 0.15
  в последние 20 секунд: там рынок реагирует быстрее вас.
- Итог смешивается со **сглаженным** рыночным microprice (EWMA, полупериод
  `STRAT_FAIR_MID_SMOOTHING_HALFLIFE_S`) и **жёстко клипуется** в пределах
  `±max_model_deviation` от него.
- Если начало окна не наблюдалось, реализованная часть неизвестна — модель
  для рынка не включается вовсе (чистый MM по рынку). Это не деградация, а
  честность: вероятности среднего без его реализованной части не существует.

### Проблема страйка

Страйк — значение ряда резолюции в НАЧАЛЕ окна (`price at the beginning of
that range`). Если бот стартовал в середине окна, этот момент уже прошёл и
через API недоступен. Стратегии, по убыванию надёжности:

1. **Наблюдали начало окна** — движок ловит пересечение `start_ts`
   (timestamp в хвосте слага) и записывает значение фида в этот момент.
2. **Парсим описание рынка** — берём число, ближайшее к текущей цене.
3. **Инвертируем TWAP-модель** — находим `K`, при котором модель даёт
   текущий рыночный mid (нужна реализованная часть окна). Дальше edge
   возникает из *расхождения* движения фида и движения рынка: торгуем
   изменение, а не уровень.

Если страйк определить не удалось, модель для рынка отключается
автоматически, и бот работает как чистый MM по рынку. Сторож расхождения
(`STRAT_STRIKE_DIVERGENCE_*`) дополнительно снимает страйк, который модель
систематически опровергает рынком.

## Установка

Требуется **Python 3.11+**.

```bash
git clone <your-repo> polymarket-hft-bot
cd polymarket-hft-bot

python3.11 -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate

pip install -r requirements.txt
```

> **Про SDK.** Старый `py-clob-client` заархивирован Polymarket в мае 2026.
> Проект использует новый официальный unified SDK: пакет
> `polymarket-client`, импорт `polymarket`. Если вы читали старые гайды с
> `from py_clob_client.client import ClobClient` — это устаревший API.

### Настройка `.env`

```bash
cp .env.example .env
```

Заполните минимум:

```ini
POLYMARKET_PRIVATE_KEY=0x<64 hex символа>
POLYMARKET_WALLET_ADDRESS=      # адрес proxy-кошелька, если он используется
DRY_RUN=true                    # НЕ МЕНЯЙТЕ, пока не пройдёте все этапы ниже
```

API-креды (`POLYMARKET_API_KEY/SECRET/PASSPHRASE`) можно оставить пустыми —
бот выведет их из приватного ключа при первом запуске.

### Предварительные требования на стороне блокчейна

1. **USDC на Polygon** (chain ID 137) на торговом кошельке.
2. **Аппрувы контрактов.** Без них ордера будут отклоняться. Разово:

```python
import asyncio
from polymarket import AsyncSecureClient
import os

async def main():
    c = await AsyncSecureClient.create(private_key=os.environ["POLYMARKET_PRIVATE_KEY"])
    print(await c.get_trading_approvals_state())
    await c.setup_trading_approvals()
    await c.close()

asyncio.run(main())
```

## Протокол тестирования — не пропускайте этапы

### Этап 1. Юнит-тесты (0 риска, 0 денег)

```bash
pytest tests/ -v
```

84 теста проверяют инварианты: полная стоимость пары (**биды плюс
комиссия**) всегда ниже `max_pair_cost`, котировки никогда не пересекают ask,
inventory skew двигает цены в правильную сторону, лимиты риска срабатывают,
модель не взрывается при `τ → 0`, позиции прошлой сессии попадают в учёт до
первого котирования, merge уходит на биржу в базовых единицах, филл
читается из НАШЕЙ ноги трейда (а не тейкерской), повторные события трейда
не задваивают позицию, mark-out делит филлы на пары и односторонние, а
единицы каждого вызова SDK закреплены канарейками (`tests/test_units.py`).

Тесты движка требуют установленного пакета `polymarket` (сеть и ключи не
нужны, клиент подменён заглушкой). Без пакета они пропускаются, а не падают.

### Этап 2. Симулятор (0 риска, 0 денег)

```bash
python simulate.py --runs 200 --window 600
```

**Обязательно прогоните чувствительность к adverse selection.** Для этого
есть режим sweep: все уровни прогоняются на ОБЩИХ seed-ах (common random
numbers) и сравниваются парно — так эффект уровня отделяется от шума
между окнами:

```bash
python simulate.py --runs 2000 --sweep 0.2,0.35,0.5,0.65 --jobs 4
```

Симулятор по умолчанию включает **трендовый режим**: в доле `--trend-prob`
окон (0.25) спот получает устойчивый снос силой `--trend-strength` сигм
окна (1.5), а поток тейкеров становится односторонним — в аптренде
агрессоры покупают YES, то есть выносят ваши BUY-NO биды, а YES-биды
голодают. Статистика всегда разделяется по трендовым и спокойным окнам.
Симулятор моделирует и **разгрузку перекоса** — точную копию
`_unwind_if_needed` движка, включая ужатие лимита у экспирации
(`--no-unwind` возвращает прежнее поведение без разгрузки).

Выход на дефолтных параметрах (2000 прогонов на уровень, 95% CI;
резолюция TWAP и фильтр краёв — как в живых рынках и движке):

| toxicity | Все окна | Спокойные (75%) | Трендовые (25%) |
|---|---|---|---|
| 0.20 | +2.1 ± 1.0 | +7.5 ± 1.2 | −14.4 ± 1.7 |
| 0.35 | −1.2 ± 0.9 | +3.2 ± 1.0 | −14.5 ± 1.5 |
| 0.50 | **−3.8 ± 0.8** | +0.2 ± 0.9 | −15.7 ± 1.2 |
| 0.65 | −5.3 ± 0.7 | −2.0 ± 0.8 | −15.3 ± 1.1 |

**Читайте эту таблицу как главный вывод проекта — теперь их три.**

1. Прибыльность спокойных окон целиком определяется тем, насколько
   информирован поток, который вас исполняет. Это не параметр, которым вы
   управляете — но он измеряется в проде: модуль mark-out
   (`src/markout.py`) считает по каждому реальному филлу, куда пошёл
   рынок через 5/30/120 секунд после исполнения.
2. **Переход на честную TWAP-резолюцию сдвинул точку безубыточности с
   toxicity ≈ 0.5 до ≈ 0.28.** Разложение на общих seed'ах (три мира:
   старый endpoint без фильтра краёв → + фильтр → + TWAP): фильтр краёв
   стоит −0.8…−1.3 USDC/окно при низкой toxicity и ноль при высокой
   (в симуляторе крайние котировки исполнялись и зарабатывали; вживую
   у них отвратительное соотношение риска к награде — фильтр оставлен);
   сама TWAP-резолюция забирает −5.2…−5.6 из спокойных окон при любой
   toxicity. Механика: среднее «запирается» по ходу окна, вероятность
   рынка насыщается к 0/1 раньше, котируемых секунд меньше (доля пар
   57% → 50%). Прежняя экономика была посчитана для игры, в которую
   эти рынки не играют.
3. Трендовые окна теряют ~14.4–15.7 USDC **при любой toxicity**: урон
   тренда — не adverse selection, а структура (доля пар падает до ~12%,
   остаток сидит на проигрышной стороне). TWAP-резолюция смягчает урон
   на +1.4…+2.9 против endpoint: шип и хвост тренда двигают среднее
   слабее, чем конечную цену.

**Гипотеза «TWAP снижает чувствительность к toxicity»** проверена парно:
наклон PnL между toxicity 0.2 и 0.65 — −8.7 ± 1.2 в endpoint-мире против
−7.4 ± 1.0 в TWAP-мире; парная разность наклонов +1.26 ± 1.36 —
**статистически неразличима** на 2000 окон. Направление совпадает с
гипотезой, но доказанного смягчения по каналу toxicity нет; значимое
смягчение TWAP даёт в другом месте — в трендовых окнах (см. вывод 3).

### Разгрузка перекоса: смоделирована, и оценки пересчитаны

Раньше симулятор не моделировал `_unwind_if_needed` движка — и это
завышало урон тренда как артефакт модели. Заодно вскрылся баг в самом
движке: `build_unwind_quotes` ставил SELL ПО цене лучшего бида, а такой
post_only-ордер marketable — биржа отклоняет его, то есть вживую
разгрузка не исполнилась бы ни разу. Исправлено (аск на тик выше бида) и
закрыто тестом.

Сравнение до/после на общих seed-ах (`--unwind-compare`, 2000 окон,
TWAP-мир; toxicity 0.5):

| Группа | Без разгрузки | С разгрузкой | Δ |
|---|---|---|---|
| Трендовые | −21.2 ± 1.7 | **−15.7 ± 1.2** | **+5.5 ± 1.4** |
| Спокойные | +0.3 ± 1.2 | +0.2 ± 0.9 | −0.1 ± 1.0 (неразличимо) |
| Все | −5.0 | −3.8 | +1.3 ± 0.8 |

В endpoint-мире разгрузка была разменом (трендовые +6.7, спокойные
−3.5…−5.7); в TWAP-мире она стала **строго лучше**: защита в трендах
сохранилась, а цена в спокойных окнах стала неразличимой от нуля —
среднее насыщает вероятность раньше, и разгрузочный SELL замещает
котирование, которое всё равно уже не складывало пары. |остаток|
трендового окна падает с 81 до 42 shares.

### Свип RISK_MAX_NET_EXPOSURE: лимит выше порога разгрузки мёртв

`--net-sweep 30,60,90,120,180` (2000 окон, общие seed-ы; порог разгрузки
едет вместе с лимитом: `min(STRAT_DIRECTIONAL_MAX_NET, лимит)` — как
требует кросс-валидация конфига). Итоги при toxicity 0.5 / 0.65:

| Лимит | Все окна (0.5 / 0.65) | Спокойные | Трендовые | Смерж. пар (спок.) |
|---|---|---|---|---|
| 30 | −0.7 / −2.4 | +2.5 / +0.3 | −10.4 / −10.7 | 20 |
| **60** | **+0.4 / −1.5** | +6.1 / +3.5 | −16.9 / −16.8 | 81 |
| 90–180 | +0.1 / −1.9 | +5.8 / +3.1 | −17.2 / −17.2 | 79 |

- **Лимиты 90/120/180 байт-в-байт одинаковы**: разгрузка на пороге 60 не
  даёт |net| дойти до жёсткого лимита — всё, что выше порога разгрузки,
  не влияет ни на что. Реальный рычаг — `STRAT_DIRECTIONAL_MAX_NET`.
- **Размен на ужесточении до 30**: +6.5…6.8 защиты в трендовых окнах
  против −2.8…−3.3 в спокойных и падения оборота вчетверо (81 → 20
  смерженных пар). Суммарно — ноль (Δ −0.5…−0.8 ± 1.0, неразличимо):
  защита оплачена целиком.
- Перемер в TWAP-мире (60 против 120, toxicity 0.5): разница
  **неразличима во всех группах** (Δ −0.00 ± 0.11) — прежний слабый
  оптимум 60 (+0.30 ± 0.24) исчез вместе со сменой резолюции.
  Практический вывод не меняется: держите `RISK_MAX_NET_EXPOSURE`
  равным `STRAT_DIRECTIONAL_MAX_NET`, выше — мёртвая зона.

Примечание: таблица размена 30/60/90–180 выше измерена в endpoint-мире;
в TWAP-мире перепроверена ключевая пара 60/120 (см. выше). Структурный
вывод «лимит выше порога разгрузки мёртв» от резолюции не зависит —
разгрузка просто не подпускает |net| к жёсткому лимиту.

### Реакция на режим: измерено и честно выключено

Бот содержит детектор режима (`src/regime.py`: односторонность потока
своих филлов, вола против своего среднего, автокорреляция спота; CALM /
TRENDING / VOLATILE с гистерезисом) и реакцию котирования: в TRENDING
сторона под выносом отодвигается или снимается, противоположная
подтягивается к рынку; в VOLATILE бот не котирует. Проверка «до/после» —
`--regime-compare`, парное сравнение на общих seed-ах:

```bash
python simulate.py --runs 2000 --toxicity 0.5 --regime-compare --jobs 4
```

Результат на 2000 окон: эффект реакции **статистически неразличим от
нуля** во всех группах. Вердикт перемерян дважды — после моделирования
разгрузки и после перехода на TWAP-резолюцию — и оба раза только
укрепился (TWAP-мир: toxicity 0.5 — спокойные Δ +0.05 ± 0.15, трендовые
Δ +0.14 ± 0.28; toxicity 0.65 — спокойные Δ +0.03 ± 0.15, трендовые
Δ +0.07 ± 0.12). Причин две, обе структурные. Во-первых, детектор,
питающийся только СОБСТВЕННЫМИ филлами, успевает войти в TRENDING, когда
позиция уже у порога разгрузки. Во-вторых, разгрузка съедает его сигнал:
продажи заменяют котирование и балансируют поток филлов в окне — в
TWAP-мире детектор проводит в TRENDING 1–2 секунды из 600 трендовых
(в endpoint-мире было 4–5, без разгрузки ~105). Обходной путь тоже
упирается в математику: при силе тренда 1.5σ за окно дрейф спота
статистически неотличим от шума изнутри окна (t-статистике нужно ~2400
секунд при окне в 600).

Поэтому `STRAT_REGIME_TRENDING_RESPONSE` по умолчанию **выключен** —
включайте только после `--regime-compare` на своих параметрах. Гейт
VOLATILE включён: он ошибается в сторону некотирования. Что реально
ограничивает урон тренда уже сейчас — `RISK_MAX_NET_EXPOSURE` (потолок
убытка окна) и разгрузка перекоса в движке; хотите меньше терять в
трендах — снижайте лимит net, платя оборотом спокойных окон. Реально
ускорить детекцию может только рыночный поток целиком (публичные трейды),
а не собственные филлы — этого в боте пока нет.

О статистике честно:

- ΔPnL — ПАРНАЯ разность на общих seed-ах; её интервал уже, чем у разности
  независимых прогонов, поэтому судить о соседних уровнях надо по ней, а
  не по перекрытию интервалов в столбце PnL.
- На 2000 прогонов все соседние уровни различимы. На 150 прогонах (старая
  таблица) разность 0.35 против 0.50 тонула в шуме — прежняя таблица даже
  показывала инверсию, которая была именно шумом. Если sweep печатает
  «СТАТИСТИЧЕСКИ НЕРАЗЛИЧИМО» — это свойство данных, а не ошибка: либо
  добавляйте прогоны, либо не делайте выводов из этой пары строк.
- Разброс PnL между окнами огромен (σ ≈ 37): единичные окна ничего не
  говорят о матожидании.
- Числа не сравнимы с прежними версиями таблицы: генератор случайности
  перестроен на раздельные потоки (траектория/шум рынка/очередь/шоки), а
  с сентября 2026 симулятор резолвит окна по TWAP и применяет фильтр
  краёв — как живые рынки и движок. Прежний endpoint-мир воспроизводится
  флагом `--resolution endpoint` (континуитет проверен: старые таблицы
  воспроизводятся с точностью до сотых).

Комиссия рынка и газ merge моделируются, но задержки сети, реджекты и
частичные исполнения — нет, поэтому цифры остаются верхней границей.

Отдельно прогоните рынок с комиссией — маржа пары там меньше:

```bash
python simulate.py --runs 500 --toxicity 0.5 --fee-rate 0.005
```

### Ликвидити-награды: формула, что известно, что нет, и перемер безубыточности

До этого раздела награды программы ликвидности не входили ни в симулятор,
ни в расчёт экономики. Ниже — что удалось установить по документации
(страница `docs.polymarket.com/programs/liquidity-rewards` для нашей среды
разработки закрыта; структура собрана по её поисковым сниппетам и
сторонним разборам и **подлежит сверке по живой странице**), что читается
из полей рынка, и что даёт симулятор.

**Формула программы (стандартная и «Up/Down TWAP rewards» — одна и та же).**

- Каждый резтинг-ордер размером ≥ `rewardsMinSize` в пределах
  `rewardsMaxSpread` (v, в центах от mid) получает очки
  `S = ((v − s)/v)² · size`, где s — расстояние от «size-cutoff-adjusted
  midpoint» (mid по книге без ордеров мельче минимального размера — защита
  от «пиннинга» mid пылью; точное определение в сниппетах не приведено).
  Вес квадратичный: ордер у mid стоит непропорционально дороже ордера в
  паре центов.
- `Q_one` — сумма очков бидов, `Q_two` — асков (наш BUY NO — это аск YES
  по 1 − p, аск разгрузки — тоже аск).
  `Q_min = max(min(Q_one, Q_two), max(Q_one, Q_two)/c)` при mid в
  [0.10, 0.90] — односторонняя ликвидность засчитывается с делителем c
  («in-game multiplier»; его значение для крипторынков в доступных
  источниках не названо, 3 — распространённая цифра, **не проверена**);
  вне диапазона засчитывается только двусторонняя: `Q_min = min(...)`.
- Выборка раз в минуту. В выборке доля мейкера = `Q_min / Σ Q_min` по
  всем мейкерам рынка; сумма долей за эпоху (сутки) нормируется по всем
  мейкерам (`Q_final = Q_epoch / Σ Q_epoch`) и умножается на пул рынка
  (`rewardsDailyRate`). Требования к аптайму как такового нет — аптайм
  входит через число выборок, в которых у нас есть очки; двусторонность
  нужна только на краях диапазона.
- Выплата раз в сутки (~00:00 UTC), минимум $1; ниже не платят.
- Следствие для 5- и 15-минутных рынков: выборки, где очков нет ни у кого,
  не входят ни в чей счёт, поэтому пул рынка делится между теми, кто
  котировал в его несколько минут жизни. «Дневная ставка» такого рынка —
  ставка **на рынок за его жизнь**, а не пропорция суток.

**Программа «$1M за август 2026».** По анонсу от 7 августа 2026 (вместе с
переводом резолюции на Chainlink TWAP: 30 с для 5m, 60 с для 15m и 4h)
Polymarket раздаёт $1M за август только на рынках с TWAP-резолюцией:
5m — $550k (BTC $300k), 15m — $350k, 4h — $100k; SOL/ETH/HYPE/XRP по $50k
на 5m, $25k на 15m, $10k на 4h, BNB/DOGE — вдвое меньше. Механика та же,
что у стандартной программы (те же поля рынка и та же формула), отличие —
размер пулов и адресность. Пул серии делится между всеми её рынками месяца
(5m — 288 рынков в сутки на актив): при равном делении это ≈ $33.6 на один
BTC-5m рынок — **это арифметика анонса, а не проверенная ставка**; реальная
`rewardsDailyRate` каждого рынка читается из `clobRewards` и печатается
`diag.py`. Свидетельств продления программы на сентябрь не найдено.

**Что читает `diag.py`.** Для каждого найденного рынка: `rewardsMaxSpread`,
`rewardsMinSize`, `holdingRewardsEnabled`, каждую запись `clobRewards`
(ставка, сумма, даты, актив) и окно TWAP резолюции. В разделе паритета для
взятых ботом рынков — стакан YES по формуле наград: adjusted mid, `Q_one`,
`Q_two` в пределах max_spread и границы суммы `Q_min` других мейкеров
`[max(Q_one, Q_two)/c; Q_one + Q_two]` — число для `--reward-competition`.

**Что в симуляторе.** Награда — отдельная строка PnL (`reward_pnl`,
`pnl_total`), торговля от неё не зависит. Раз в минуту считается `Q_min`
наших котировок по формуле выше, доля выборки — `Q_min / (Q_min +
competition)`, доля пула — среднее по выборкам, где очки есть хоть у кого-то
(без конкуренции — ровно 1: пул достаётся целиком, сколько бы минут мы ни
котировали; это верхняя граница, а не оценка). Флаги: `--reward-max-spread`
(включает награды), `--reward-min-size`, `--reward-daily-rate` (пул рынка,
USDC за его жизнь), `--reward-competition`, `--reward-c`. Помимо награды
печатаются пригодность (доля минут с нашими очками) с разбором промахов,
средний `Q_min` и **пул рынка, при котором торговый PnL выходит в ноль при
текущей доле**.

**Перемер на TWAP-резолюции** (2000 окон на уровень, общие seed'ы,
`--reward-max-spread 3.5 --reward-min-size 20`, ставка 0 — только метрики).
Столбцы «без полей» и «с полями» — один и тот же бот, разница только в
том, что параметры программы наград заданы у рынка: quoting зажимает
полуспред в max_spread и поднимает размер до min_size.

Выводы:

1. **На 5-минутных рынках торговый PnL отрицателен при любой toxicity от
   0.2** — точки безубыточности без наград в измеренном диапазоне нет.
   Пул на рынок, закрывающий убыток при доле пула 1: от 0.9 (toxicity
   0.2) до 7.1 USDC (0.65). На 15-минутных безубыточность без наград —
   toxicity ≈ 0.39 (≈ 0.44 с полями наград); при 0.5 нужен пул 1.3, при
   0.65 — 3.4 USDC на рынок.
2. **Если пул одного BTC-5m рынка действительно порядка десятков USDC**
   (арифметика августовского анонса), награды не поправка к экономике, а
   её основа: даже доля пула 0.15 (пример: Q_min ≈ 6 против конкуренции
   ≈ 8 — как в `python simulate.py --runs 150 --toxicity 0.5
   --reward-max-spread 3.5 --reward-daily-rate 30 --reward-competition 8`)
   перекрывает торговый убыток на любой toxicity. Поэтому первые числа,
   которые надо снять с живого API, — `rewardsDailyRate` и стакан — а не
   toxicity.
3. **Пригодность 30–45%**, и почти весь промах — фильтр краёв: mid вне
   [0.10, 0.90] на 55–70% минут окна (TWAP-вероятность насыщается по ходу
   окна). Разгрузочный аск засчитывается односторонне (делитель c), поэтому
   разгрузка пригодность не съедает.
4. **`rewardsMaxSpread` в диапазоне 2–5¢ на результат не влияет вовсе**
   (три свипа совпали побайтно): наши котировки либо в пределах ~2¢ от
   mid (медиана 1.2¢), либо — когда модель расходится с рынком — дальше
   5¢, где очков нет при любом v.
5. **Поля наград меняют торговый PnL** на ±0.4 USDC/окно и поднимают
   |остаток| на ~15%: пол `rewards_min_size` в `_size_for` срабатывает
   ПОСЛЕ инвентарного дросселя и на рынке с min_size ≥ order_size отменяет
   его. Оставлено как есть и записано в незакрытые задачи: выбор «награда
   или дроссель» — по живой ставке пула, не по симулятору.

**Чего для честной модели не хватает — снять с живого API:**

- `rewardsDailyRate` и даты каждого рынка (`clobRewards`) — `diag.py`;
  без них награда в симуляторе — только «нужный пул».
- Конкуренция: сумма `Q_min` других мейкеров считается на мейкера и по
  книге не восстанавливается точно — `diag.py` печатает границы; точнее
  только по факту выплат (дашборд наград) за первые сутки.
- Значение c для крипторынков и точное определение adjusted midpoint.
- Продолжается ли программа после августа 2026 и в каком размере.
- Сверка модели с фактическими выплатами: доля пула по выплате против
  расчётной — единственная проверка, что нормировка понята верно.

### Лестница котировок и наблюдаемый мейкер: что подразумевает его результат

Живой кошелёк-мейкер на тех же рынках (Polkadot-Frog: $139K PnL с мая,
56K сделок, рабочий капитал $1.9K) делает структурно нашу стратегию: обе
стороны, merge полных пар, направленный остаток. Наблюдаемые отличия: сумма
пар 0.96–0.98 (шире наших 0.985); лестница из 5–6 ордеров на сторону

распространяется на любую пару уровней: любая пара глубже лучшей —
дешевле. Ключ дедупликации ордера теперь `(token, side, level)`; после
реконнекта уровни восстанавливаются по цене; финальный клип движка считает
запас лимитов накопительно по уровням. Дефолт — один уровень, поведение
прежнее.

### 5-минутные против 15-минутных: в час и при равном капитале

Уточнение по эталонному кошельку: он работает на 5-минутных рынках и
мержит на них же («Объединить 126.9 долей → $126.87» на BTC 2:45–2:50), а
симулятор выше показал, что 5m убыточны при любой toxicity от 0.2. Две
гипотезы, что упущено: (а) на 5m доля неинформированного розничного потока
выше — прогнаны toxicity 0.05, 0.10, 0.15; (б) сравнивать надо не PnL за
окно, а за час: 5m даёт втрое больше окон и втрое быстрее оборот капитала
через merge и резолюцию.

капитал — максимум себестоимости инвентаря на руках за окно (merge и
резолюция его возвращают). Это и есть сравнение при равном капитале:
короткое окно занимает деньги ненадолго, и один и тот же капитал за час

### Этап 3. Dry run на живых данных (0 риска, 0 денег)

Перед dry run — быстрая проверка, что бот вообще увидит рынки:

```bash
python diag.py
```

Скрипт читает публичный Gamma API (ключи и `.env` не нужны, ордеров у него
нет физически) и печатает: что возвращают настроенные `STRAT_SERIES_SLUGS`,
какие открытые серии содержат `up-or-down`/`updown`/`twap` в слаге, что
находит поиск по заголовкам, таблицу рынков с временем до экспирации,
`accepting_orders`, `enable_order_book` и token_id обеих ног — и воронку
фильтров бота (сколько кандидатов отсеял каждый фильтр). Код выхода 0 —
бот взял бы рынок прямо сейчас; 2 — нет, и в выводе видно, почему. Если
слаги устарели, актуальные видны в разделах 3–4 вывода — пропишите их в
`.env`.

```bash
DRY_RUN=true python run.py
```

Бот подключается к реальным фидам, находит рынки, считает fair value и
логирует котировки, **не отправляя ни одного ордера**. Дайте ему поработать
не меньше часа и проверьте:

- Находятся ли рынки? (`Новый рынок: BTC | до экспирации ...` и строка
  `discovery: ...` с воронкой фильтров каждые 20 секунд)
- Жив ли фид резолюции ПО КАЖДОМУ активу И ОКНУ? Ждите четыре строки:
  `Фид резолюции: первый тик BTC@30s (symbol='btc/usd' ...)`, `BTC@60s`
  и такие же для ETH — 5-минутные рынки резолвятся по 30-секундному TWAP,
  15-минутные по 60-секундному, фид подписан на оба потока и ведёт серии
  раздельно. Топиковая подписка начинается с чужих символов (вживую первым
  пришёл zec/usd), и общий «первый тик» ни о чём не говорил. Если через 30
  секунд какой-то серии нет — бот сам напишет WARNING со списком
  отсутствующих (`BTC@30s` и т.п.).
- Прогрев модели: sigma по потоку TWAP-60 оценивается лаг-выборкой раз в
  60 секунд — готовность через ~12 минут фида, до этого модель живёт на
  floor-подмешанной sigma. Это следствие сглаженности ряда резолюции, а
  не бага.
- Детектор режима: первые ~5 минут в статусной строке `РЕЖИМ` должно быть
  `vol_ready: False` и `regime: calm` при любом `vol_ratio_raw` — это
  прогрев медленной EWMA. Ложный `volatile` на старте — баг, а не рынок.
- Определяется ли страйк? Ищите `Страйк из наблюдения открытия окна` (лучший
  случай) или `Страйк калиброван по живому рынку: K=... (spot=... mid=...
  sigma=...)`. Строка `Модель устойчиво расходится с рынком` = сторож снял
  ложный страйк; если он срабатывает на каждом рынке — модель системно
  смещена (проверьте семантику резолюции, см. «Известные ограничения»).
- Не «дёргается» ли fair value? Резкие скачки = проблема с фидом.
- Держится ли сумма пары ниже `max_pair_cost`? Обратное отклонение —
  `Сумма пары ... существенно ниже цели` в WARNING — признак сломанного

## Мониторинг

```bash
tail -f logs/bot.log                                    # общий лог
jq -c 'select(.event=="fill")'   logs/trades.jsonl      # исполнения
jq -c 'select(.event=="merge")'  logs/trades.jsonl      # merge пар
jq -c 'select(.event=="reject")' logs/trades.jsonl      # отказы
jq -s 'map(select(.event=="status")) | last' logs/trades.jsonl
```

Строка статуса раз в 30 с:

```
СТАТУС | рынков=2 ордеров=4 | пар=45 смержено=320 net=-8 | PnL=2.4310 филлов=64 | комиссии=0.0000 газ=0.1600 | OK
```

**На что смотреть в первую очередь:** доля реджектов (высокая = проблема с
ценами или аппрувами), `net` (должен колебаться вокруг нуля, а не расти),
отношение `смержено` к `филлов` (низкое = пары не складываются, вы копите
одностороннюю позицию), `газ` против `PnL` (сопоставимые величины = мержите
слишком мелкими пачками, поднимите `STRAT_MIN_MERGE_SIZE`).

Отдельно стоит грепать события-сигналы:

```bash
jq -c 'select(.event=="recover")'           logs/trades.jsonl
jq -c 'select(.event=="fee_mismatch")'      logs/trades.jsonl
jq -c 'select(.event=="position_desync")'   logs/trades.jsonl
jq -c 'select(.event=="fill_unattributed")' logs/trades.jsonl
jq -c 'select(.event=="markout")'           logs/trades.jsonl
```

`recover` — что бот нашёл на кошельке при старте; если там непустая позиция,
а вы её не ждали, разбирайтесь до того, как он начнёт котировать.
`fee_mismatch` — биржа списала комиссию с рынка, который бот считал
бесплатным: расчёт маржи пары был занижен. `position_desync` — локальный
учёт разошёлся с биржей (action=correct — скорректировано, action=halt —
остановка). `fill_unattributed` — пришёл трейд, не сопоставленный ни одному
нашему ордеру: он НЕ учтён, сверка позиций подберёт расхождение.

### Mark-out: насколько токсичен ваш поток

Симулятор показывает, что прибыльность решает adverse selection, — mark-out
измеряет её на реальных филлах. Каждые 30 с в статусе три строки:

```
MARKOUT | 5s: paired=+0.0011 (n=34) solo=-0.0038 (n=12) unwind=- | 30s: ... | 120s: ...
MARKOUT по стороне | 5s: YES=-0.0007 (n=25) NO=+0.0004 (n=21) | ...
MARKOUT по горизонту рынка | 5s: 15m/paired=+0.0009 (n=20) 15m/solo=-0.0021 (n=7) 5m/paired=+0.0014 (n=14) 5m/solo=-0.0061 (n=5) | ...
```

Числа — средний mark-out на одну share (USDC), взвешенный размером.
Третья строка — те же корзины отдельно по длительности окна рынка (из
слага: `btc-updown-5m-…` → `5m`, `…-15m-…` → `15m`; рынок без
распознаваемого хвоста — `?`). Именно она отвечает на вопрос «где
экономика лучше — на 5-минутных или 15-минутных»: симулятор здесь даёт
только модельный ответ (раздел про лестницу и наблюдаемого мейкера), а
живые филлы — настоящий. Сравнивайте `5m/solo` с `15m/solo` на горизонте
30–120 с при сопоставимом `n`: горизонт с менее отрицательным solo при
той же марже пары — тот, где поток менее токсичен. То же в `trades.jsonl`:
поле `market_horizon` у каждого события `markout` и блок `market_horizon`
в событии `status`.

**Как читать.** `solo` — главная корзина: это односторонние остатки, по
которым движение рынка бьёт прямо в PnL. Если solo на горизонтах 30–120 с
стабильно отрицательный и глубже маржи пары (при дефолтах ~1.5 цента),
поток против вас токсичнее, чем закладывает спред, — сворачивайтесь или
расширяйте спред. `paired` — качество цен входа собранных пар: пара уже
стоит $1, ей рынок не страшен. `unwind` — качество исполнения разгрузки.
Перекос между YES и NO — систематическая ошибка модели или страйка.
`miss` — замер пришёлся на истёкший рынок (книги уже нет): точка честно
пропущена, а не выдумана.

## Известные ограничения

- **Один страйк на рынок.** Если Polymarket поменяет формат серий Up-or-Down,
  `discovery.py` потребует правки. Слаги серий вынесены в конфиг.
- **Поиск рынков идёт через title_search.** Живые updown-рынки
  (`btc-updown-5m-*`, `*-15m-*`) находятся полнотекстовым поиском; их слаги
  серий неизвестны, и путь через `list_series` — только резерв
  (`STRAT_SERIES_SLUGS`, по умолчанию пуст). Актуальную картину показывает
  `python diag.py` (разделы 3–4).
- **Страйк определяется по живым данным и может быть снят сторожем.**
  Лучший источник — спот в момент открытия окна (start_ts из слага);
  резерв — инверсия GBM по живому mid, споту и sigma. Если |model − mid|
  держится выше `STRAT_STRIKE_DIVERGENCE_THRESHOLD` дольше
  `STRAT_STRIKE_DIVERGENCE_HOLD_S`, страйк признаётся ложным и модель для
  рынка отключается (после второго срыва — до конца окна): бот продолжает
  чистый MM вокруг рыночной цены.
- **Резолюция по TWAP подтверждена и реализована, но механика усреднения
  на стороне рынка — наша интерпретация.** Мы усредняем тики потока
  Chainlink TWAP-60s ступенчатым интегратором; если Polymarket усредняет
  по своим точкам, реализованная часть чуть разойдётся. Систематическое
  расхождение всплывёт сторожем страйка и mark-out'ом.
- **Бот, стартовавший в середине окна, не торгует моделью до следующего
  окна.** Реализованная часть TWAP невосстановима — модель честно молчит,
  бот работает чистым MM по рынку (или ждёт следующего окна: 5-минутки
  приходят каждые 5 минут).
- **Merge требует газа** на Polygon. Издержки заведены в PnL
  (`STRAT_MERGE_GAS_COST`), и merge не отправляется, пока прибыль пачки не
  превысит газ в `STRAT_MERGE_MIN_PROFIT_RATIO` раз. Но сама цена газа —
  константа из конфига, а не факт из чека транзакции: при скачке цены POL
  реальные издержки окажутся выше учтённых.
- **Восстановление позиций не заменяет ручной проверки.** При старте бот
  читает `list_positions()` и заводит найденное в учёт, а сторону (YES/NO)
  подтверждает по `token_id`, когда находит рынок. Но позиции по рынкам,
  которые бот больше не котирует, остаются висеть: он их видит, а закрыть
  не может — они вне его окна торговли.
- **Окно TWAP резолюции читается из описания рынка** (ссылка вида
  `…-twap-30s-…`), резерв — длительность из слага (5m → 30 с, 15m/4h →
  60 с). Рынок, у которого окно определить нельзя, бот не берёт — это
  видно в воронке (`окно_twap=`). Если Polymarket сменит окна, менять
  нужно `TWAP_WINDOW_BY_DURATION_S` в `discovery.py` и `TWAP_WINDOWS`
  в `price_feed.py`.
- **Ликвидити-награды — верхняя граница без живых чисел.** Формула
  собрана по сниппетам документации, пул рынка, конкуренция, значение c
  и продолжение программы известны только с живого API (см. раздел про
  награды в Этапе 2). Бот награды не «зарабатывает» осознанно: quoting
  лишь зажимает полуспред в `rewards_max_spread` и поднимает размер до
  `rewards_min_size` — второе отменяет инвентарный дроссель на рынках с
  min_size ≥ order_size.
- **Rate limits.** Заданы консервативно (25 операций/с). При агрессивных
  настройках Polymarket может начать отклонять запросы.
- **Комиссии смоделированы по расписанию рынка, а не по факту.** Ставка и
  экспонента читаются из `fee_schedule` и вычитаются из маржи пары. Если
  расписание помечено `taker_only`, бот считает рынок для себя бесплатным:
  все его ордера `post_only`, то есть он всегда мейкер. Если биржа всё же
  спишет комиссию с нашего филла, бот поднимет ставку по факту и расширит
  спред — но одна пара к тому моменту уже будет собрана дороже расчёта.
