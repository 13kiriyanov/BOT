# Polymarket Short-Term Crypto Market Maker

Бот для маркет-мейкинга на краткосрочных (5–15 мин) рынках BTC/ETH Up-or-Down
на Polymarket CLOB. Стратегия: двустороннее котирование с накоплением полных
пар, мгновенный merge пар в USDC, управление инвентарём и слабый directional
наклон от модели fair value по споту.

**Почему именно здесь потерять деньги особенно легко:**

- **Adverse selection.** Маркет-мейкинг на 5-минутных крипторынках — среда, где
  против вас торгуют участники с колокацией и прямыми фидами бирж. Ваш ордер
  исполняется чаще всего именно тогда, когда цена собирается пойти против вас.
  Симулятор в этом репозитории показывает: при доле информированного потока
  выше ~0.6 стратегия становится убыточной. Оценить эту долю заранее нельзя.
- **Нет тестнета.** Polymarket не предоставляет sandbox или paper-trading.
  Любая проверка на живом рынке — это реальные деньги.
- **Технический риск.** Разрыв WebSocket, зависший цикл, изменение API,
  расхождение локального учёта позиций с реальностью — каждое из этого может
  привести к неконтролируемой позиции. Риск-модули здесь снижают вероятность,
  но не устраняют её.
- **Модельный риск.** Страйк рынка часто приходится калибровать косвенно
  (см. раздел «Проблема страйка»). Неверный страйк = систематически смещённая
  оценка = систематические убытки.
- **Юридический риск.** Вы обязаны самостоятельно проверить geo-restrictions
  Polymarket, их Terms of Service и законодательство своей юрисдикции
  **до** запуска. В ряде стран доступ к платформе ограничен, а
  автоматизированная торговля событийными контрактами может подпадать под
  регулирование.

**Это не финансовая рекомендация.** Автор кода не несёт ответственности за
ваши убытки. Используйте отдельный кошелёк с суммой, потеря которой не
изменит вашу жизнь.

## Как это на самом деле работает

### Поправка, которую важно понять до запуска

Распространённое заблуждение: «ищем рынки, где `yes_ask + no_ask < 0.99`, и
покупаем обе стороны». **Такой возможности не существует.** Матчинг-движок
Polymarket трактует YES и NO как дополняющие друг друга: покупка NO по цене
`p` тождественна продаже YES по `1 − p`. Стаканы зеркальны:

```
ask_NO ≡ 1 − bid_YES
bid_NO ≡ 1 − ask_YES
```

Тейкерский арбитраж внутри одного рынка арбитражируется самим движком.

Реальная стратегия — **мейкерская**. Мы ставим `BUY YES @ a` и `BUY NO @ b`
так, что `a + b < 1`, и ждём пассивного исполнения обеих ног. Получив пару,
имеем актив, стоящий ровно $1 при любом исходе, купленный за `a + b`.

При этом заметьте:

```
bid_YES = a
ask_YES = 1 − b          (покупка NO по b == продажа YES по 1−b)
spread  = 1 − (a + b)
```

**«Накопление пар с суммой 0.985» и «котирование с полуспредом 0.75 цента
вокруг fair value» — это буквально одно и то же действие.** Поэтому в боте
один модуль (`quoting.py`) делает и то, и другое: вы задаёте целевую
стоимость пары, из неё выводится спред.

### Откуда берётся прибыль (по убыванию значимости)

1. **Захват спреда на обеих ногах.** Основа. `1 − target_pair_cost` за пару.
2. **Мгновенный merge.** `merge_positions()` превращает пару YES+NO обратно в
   $1 USDC, не дожидаясь резолюции. Без этого капитал заморожен до конца
   окна, и бот делает 1–2 круга вместо десятков. **Это то, что делает
   стратегию высокочастотной.**
3. **Liquidity rewards.** У многих рынков есть `rewards_max_spread` и
   `rewards_min_size`. Котирование внутри этой полосы приносит выплаты,
   часто сопоставимые с торговым PnL. Бот автоматически ужимает спред внутрь
   reward-полосы.
4. **Directional edge.** Самый маленький и самый рискованный компонент.
   Его роль — не «заработать на направлении», а **не оказаться на
   неправильной стороне**, когда BTC двинулся, а рынок ещё не переставился.

### Модель fair value

Под GBM вероятность того, что цена закроется выше страйка:

```
P(S_T > K) = Φ( (ln(S/K) + μτ − σ²τ/2) / (σ√τ) )
```

Практические поправки, без которых модель бесполезна на минутных горизонтах:

- `σ` — EWMA реализованной волатильности по тикам спота (полупериод 45 с).
  Статичная волатильность на таком горизонте не работает.
- `μ` — momentum из EWMA доходностей, **зажатый в одно стандартное
  отклонение**. Momentum крипты на минутах шумный; без клипа он утаскивает
  оценку в крайности.
- При `τ → 0` модель сингулярна. Доверие к ней (`confidence`) падает до 0.15
  в последние 20 секунд: там рынок реагирует на спот быстрее вас.
- Итог смешивается с рыночным microprice и **жёстко клипуется** в пределах
  `±max_model_deviation` от него. Если модель говорит 0.30, а рынок 0.62 —
  сломана модель, а не рынок.

### Проблема страйка

Рынок «Bitcoin Up or Down 3PM ET» резолвится сравнением цены на экспирации с
ценой на открытии окна. Если бот стартовал в середине окна, этот момент уже
прошёл и через API часто недоступен. Три стратегии, по убыванию надёжности:

1. **Наблюдали открытие** — используем записанный спот.
2. **Парсим описание рынка** — берём число, ближайшее к текущему споту.
3. **Инвертируем GBM** — находим `K`, при котором модель даёт текущий
   рыночный mid. Модель калибруется на рынок в момент `t₀`, и дальше edge
   возникает из *расхождения* движения спота и движения рынка. Торгуем
   изменение, а не уровень.

Если страйк определить не удалось, directional-компонент для этого рынка
отключается автоматически, и бот работает как чистый MM по рынку.

## Установка

Требуется **Python 3.11+**.

```bash
git clone <your-repo> polymarket-hft-bot
cd polymarket-hft-bot

python3.11 -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate

pip install -r requirements.txt
```

> **Про SDK.** Старый `py-clob-client` заархивирован Polymarket в мае 2026.
> Проект использует новый официальный unified SDK: пакет
> `polymarket-client`, импорт `polymarket`. Если вы читали старые гайды с
> `from py_clob_client.client import ClobClient` — это устаревший API.

### Настройка `.env`

```bash
cp .env.example .env
```

Заполните минимум:

```ini
POLYMARKET_PRIVATE_KEY=0x<64 hex символа>
POLYMARKET_WALLET_ADDRESS=      # адрес proxy-кошелька, если он используется
DRY_RUN=true                    # НЕ МЕНЯЙТЕ, пока не пройдёте все этапы ниже
```

API-креды (`POLYMARKET_API_KEY/SECRET/PASSPHRASE`) можно оставить пустыми —
бот выведет их из приватного ключа при первом запуске.

### Предварительные требования на стороне блокчейна

1. **USDC на Polygon** (chain ID 137) на торговом кошельке.
2. **Аппрувы контрактов.** Без них ордера будут отклоняться. Разово:

```python
import asyncio
from polymarket import AsyncSecureClient
import os

async def main():
    c = await AsyncSecureClient.create(private_key=os.environ["POLYMARKET_PRIVATE_KEY"])
    print(await c.get_trading_approvals_state())
    await c.setup_trading_approvals()
    await c.close()

asyncio.run(main())
```

## Протокол тестирования — не пропускайте этапы

### Этап 1. Юнит-тесты (0 риска, 0 денег)

```bash
pytest tests/ -v
```

84 теста проверяют инварианты: полная стоимость пары (**биды плюс
комиссия**) всегда ниже `max_pair_cost`, котировки никогда не пересекают ask,
inventory skew двигает цены в правильную сторону, лимиты риска срабатывают,
модель не взрывается при `τ → 0`, позиции прошлой сессии попадают в учёт до
первого котирования, merge уходит на биржу в базовых единицах, филл
читается из НАШЕЙ ноги трейда (а не тейкерской), повторные события трейда
не задваивают позицию, mark-out делит филлы на пары и односторонние, а
единицы каждого вызова SDK закреплены канарейками (`tests/test_units.py`).

Тесты движка требуют установленного пакета `polymarket` (сеть и ключи не
нужны, клиент подменён заглушкой). Без пакета они пропускаются, а не падают.

### Этап 2. Симулятор (0 риска, 0 денег)

```bash
python simulate.py --runs 200 --window 600
```

**Обязательно прогоните чувствительность к adverse selection.** Для этого
есть режим sweep: все уровни прогоняются на ОБЩИХ seed-ах (common random
numbers) и сравниваются парно — так эффект уровня отделяется от шума
между окнами:

```bash
python simulate.py --runs 2000 --sweep 0.2,0.35,0.5,0.65 --jobs 4
```

Выход на дефолтных параметрах (2000 прогонов на уровень, 95% CI):

| toxicity | Средний PnL за окно | Прибыльных окон | ΔPnL к предыдущему уровню |
|---|---|---|---|
| 0.20 | +21.6 ± 1.6 | 70.9% ± 2.0% | — |
| 0.35 | +16.2 ± 1.6 | 64.6% ± 2.1% | −5.4 ± 1.8 (различимо) |
| 0.50 | +12.1 ± 1.6 | 59.9% ± 2.1% | −4.1 ± 2.0 (различимо) |
| 0.65 | +7.3 ± 1.6 | 54.7% ± 2.2% | −4.7 ± 2.0 (различимо) |

**Читайте эту таблицу как главный вывод проекта.** Прибыльность целиком
определяется тем, насколько информирован поток, который вас исполняет. Это
не параметр, которым вы управляете — но теперь он измеряется и в проде:
модуль mark-out (`src/markout.py`) считает по каждому реальному филлу,
куда пошёл рынок через 5/30/120 секунд после исполнения.

О статистике честно:

- ΔPnL — ПАРНАЯ разность на общих seed-ах; её интервал уже, чем у разности
  независимых прогонов, поэтому судить о соседних уровнях надо по ней, а
  не по перекрытию интервалов в столбце PnL.
- На 2000 прогонов все соседние уровни различимы. На 150 прогонах (старая
  таблица) разность 0.35 против 0.50 тонула в шуме — прежняя таблица даже
  показывала инверсию, которая была именно шумом. Если sweep печатает
  «СТАТИСТИЧЕСКИ НЕРАЗЛИЧИМО» — это свойство данных, а не ошибка: либо
  добавляйте прогоны, либо не делайте выводов из этой пары строк.
- Разброс PnL между окнами огромен (σ ≈ 37): единичные окна ничего не
  говорят о матожидании.
- Числа не сравнимы с прежними версиями таблицы: генератор случайности
  перестроен на раздельные потоки (траектория/шум рынка/очередь/шоки).

Комиссия рынка и газ merge моделируются, но задержки сети, реджекты и
частичные исполнения — нет, поэтому цифры остаются верхней границей.

Отдельно прогоните рынок с комиссией — маржа пары там меньше:

```bash
python simulate.py --runs 500 --toxicity 0.5 --fee-rate 0.005
```

### Этап 3. Dry run на живых данных (0 риска, 0 денег)

```bash
DRY_RUN=true python run.py
```

Бот подключается к реальным фидам, находит рынки, считает fair value и
логирует котировки, **не отправляя ни одного ордера**. Дайте ему поработать
не меньше часа и проверьте:

- Находятся ли рынки? (`Новый рынок: BTC | до экспирации ...`)
- Определяется ли страйк, и каким из трёх способов?
- Не «дёргается» ли fair value? Резкие скачки = проблема с фидом.
- Держится ли сумма пары ниже `max_pair_cost`?
- Растёт ли `sigma` до разумных значений (0.3–1.0 для BTC)?

```bash
tail -f logs/bot.log
cat logs/trades.jsonl | jq -c 'select(.event=="place_dry")' | head -20
```

### Этап 4. Микро-депозит (реальные деньги, минимальный риск)

Переходите **только** после чистого dry run. Начните с суммы, потеря которой

Бот потребует ввести `Я ПОНИМАЮ РИСКИ` при старте с `DRY_RUN=false`.

Сидите рядом с ботом первые часы. Проверяйте: сходится ли учёт позиций с
тем, что показывает сайт Polymarket; проходят ли merge; какая доля ордеров
отклоняется.

### Этап 5. Постепенное увеличение

Повышайте лимиты не быстрее, чем в 1.5 раза за несколько дней работы, и
только если реальный PnL положителен на **сотнях** заполнений. Десяток
удачных сделок — это шум, а не подтверждение.

## Параметры конфигурации

### Стратегия

| Параметр | Умолчание | Что делает |
|---|---|---|
| `STRAT_TARGET_PAIR_COST` | 0.985 | Целевая стоимость пары. Ниже = шире спред, меньше филлов, больше маржа |
| `STRAT_MAX_PAIR_COST` | 0.995 | Жёсткая планка. Выше не котируем никогда |
| `STRAT_ORDER_SIZE` | 20 | Размер ордера в shares |
| `STRAT_MODEL_WEIGHT` | 0.35 | Вес модели против рынка. 0 = чистый MM |
| `STRAT_ALLOW_DIRECTIONAL` | true | `false` = строго дельта-нейтрально |
| `STRAT_DIRECTIONAL_MIN_EDGE` | 0.025 | Минимальный edge для направленной позиции |
| `STRAT_AUTO_MERGE` | true | Merge пар в USDC. Ключ к оборачиваемости |
| `STRAT_MERGE_GAS_COST` | 0.01 | Цена транзакции merge, USDC. Для proxy-кошелька — 0 |
| `STRAT_MERGE_MIN_PROFIT_RATIO` | 3 | Во сколько раз прибыль пачки должна превышать газ |
| `STRAT_FALLBACK_FEE_RATE` | 0.02 | Ставка комиссии, если рынок не отдал расписание |
| `STRAT_RECOVER_POSITIONS` | true | Читать позиции с биржи при старте |
| `STRAT_QUOTE_INTERVAL_S` | 0.35 | Период главного цикла. Ниже 0.15 — rate limit |

### Риск

| Параметр | Умолчание | Что делает |
|---|---|---|
| `RISK_MAX_POSITION_PER_SIDE` | 250 | Лимит на одну сторону одного рынка |
| `RISK_MAX_NET_EXPOSURE` | 120 | Направленная экспозиция по всем рынкам |
| `RISK_MAX_NOTIONAL` | 500 | Капитал в работе, USDC |
| `RISK_DAILY_LOSS_LIMIT` | 50 | Дневной убыток → полная остановка |
| `RISK_HEARTBEAT_TIMEOUT_S` | 6 | Dead-man switch |
| `RISK_STALE_PRICE_TIMEOUT_S` | 4 | Спот-фид протух → не котируем |

**Начните с значений в 5–10 раз меньше умолчаний.** Умолчания подобраны для
иллюстрации, а не для вашего счёта.

| Защита от неликвида | `risk.py` | Глубина < 50 shares → не котируем |
| Протухший фид | `risk.py` | Спот старше 4 с → не котируем |
| Post-only | `execution.py` | Ордер-тейкер отклоняется биржей |
| Инвариант пары | `quoting.py` | Сумма ≥ планки → не котируем вовсе |
| Разгрузка перекоса | `engine.py` | \|net\| > лимита → продажа излишка |
| Сокращение у экспирации | `quoting.py` | < 60 с → размеры режутся, направление снимается |
| Сверка ордеров | `execution.py` | Каждые 45 с сверка с биржей |
| Cancel all при выходе | `engine.py` | SIGINT/SIGTERM/исключение |

## Мониторинг

```bash
tail -f logs/bot.log                                    # общий лог
jq -c 'select(.event=="fill")'   logs/trades.jsonl      # исполнения
jq -c 'select(.event=="merge")'  logs/trades.jsonl      # merge пар
jq -c 'select(.event=="reject")' logs/trades.jsonl      # отказы
jq -s 'map(select(.event=="status")) | last' logs/trades.jsonl
```

Строка статуса раз в 30 с:

```
СТАТУС | рынков=2 ордеров=4 | пар=45 смержено=320 net=-8 | PnL=2.4310 филлов=64 | комиссии=0.0000 газ=0.1600 | OK
```

**На что смотреть в первую очередь:** доля реджектов (высокая = проблема с
ценами или аппрувами), `net` (должен колебаться вокруг нуля, а не расти),
отношение `смержено` к `филлов` (низкое = пары не складываются, вы копите
одностороннюю позицию), `газ` против `PnL` (сопоставимые величины = мержите
слишком мелкими пачками, поднимите `STRAT_MIN_MERGE_SIZE`).

Отдельно стоит грепать события-сигналы:

```bash
jq -c 'select(.event=="recover")'           logs/trades.jsonl
jq -c 'select(.event=="fee_mismatch")'      logs/trades.jsonl
jq -c 'select(.event=="position_desync")'   logs/trades.jsonl
jq -c 'select(.event=="fill_unattributed")' logs/trades.jsonl
jq -c 'select(.event=="markout")'           logs/trades.jsonl
```

`recover` — что бот нашёл на кошельке при старте; если там непустая позиция,
а вы её не ждали, разбирайтесь до того, как он начнёт котировать.
`fee_mismatch` — биржа списала комиссию с рынка, который бот считал
бесплатным: расчёт маржи пары был занижен. `position_desync` — локальный
учёт разошёлся с биржей (action=correct — скорректировано, action=halt —
остановка). `fill_unattributed` — пришёл трейд, не сопоставленный ни одному
нашему ордеру: он НЕ учтён, сверка позиций подберёт расхождение.

### Mark-out: насколько токсичен ваш поток

Симулятор показывает, что прибыльность решает adverse selection, — mark-out
измеряет её на реальных филлах. Каждые 30 с в статусе две строки:

```
MARKOUT | 5s: paired=+0.0011 (n=34) solo=-0.0038 (n=12) unwind=- | 30s: ... | 120s: ...
MARKOUT по стороне | 5s: YES=-0.0007 (n=25) NO=+0.0004 (n=21) | ...
```

Числа — средний mark-out на одну share (USDC), взвешенный размером.

**Как читать.** `solo` — главная корзина: это односторонние остатки, по
которым движение рынка бьёт прямо в PnL. Если solo на горизонтах 30–120 с
стабильно отрицательный и глубже маржи пары (при дефолтах ~1.5 цента),
поток против вас токсичнее, чем закладывает спред, — сворачивайтесь или
расширяйте спред. `paired` — качество цен входа собранных пар: пара уже
стоит $1, ей рынок не страшен. `unwind` — качество исполнения разгрузки.
Перекос между YES и NO — систематическая ошибка модели или страйка.
`miss` — замер пришёлся на истёкший рынок (книги уже нет): точка честно
пропущена, а не выдумана.

## Известные ограничения

- **Один страйк на рынок.** Если Polymarket поменяет формат серий Up-or-Down,
  `discovery.py` потребует правки. Слаги серий вынесены в конфиг.
- **Merge требует газа** на Polygon. Издержки заведены в PnL
  (`STRAT_MERGE_GAS_COST`), и merge не отправляется, пока прибыль пачки не
  превысит газ в `STRAT_MERGE_MIN_PROFIT_RATIO` раз. Но сама цена газа —
  константа из конфига, а не факт из чека транзакции: при скачке цены POL
  реальные издержки окажутся выше учтённых.
- **Восстановление позиций не заменяет ручной проверки.** При старте бот
  читает `list_positions()` и заводит найденное в учёт, а сторону (YES/NO)
  подтверждает по `token_id`, когда находит рынок. Но позиции по рынкам,
  которые бот больше не котирует, остаются висеть: он их видит, а закрыть
  не может — они вне его окна торговли.
- **Rate limits.** Заданы консервативно (25 операций/с). При агрессивных
  настройках Polymarket может начать отклонять запросы.
- **Комиссии смоделированы по расписанию рынка, а не по факту.** Ставка и
  экспонента читаются из `fee_schedule` и вычитаются из маржи пары. Если
  расписание помечено `taker_only`, бот считает рынок для себя бесплатным:
  все его ордера `post_only`, то есть он всегда мейкер. Если биржа всё же
  спишет комиссию с нашего филла, бот поднимет ставку по факту и расширит
  спред — но одна пара к тому моменту уже будет собрана дороже расчёта.
